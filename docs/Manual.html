SailplaneCalc — Developer Manual

A from-scratch reference for anyone extending or debugging this codebase. It documents every major module, the formulas each one implements, and why those formulas are correct — not just what the code does, but the aerodynamics/geometry theory behind it.

This app is a Python/PySide6 desktop port of two Excel workbooks — SailplaneCalc.xls and SailplaneCalcMetric.xlsx — that RC glider builders have used for years to size wings, tails, and CG. The Cl Calcs tab additionally ports LIFTROLL.xlsx, a horseshoe-vortex lift-distribution calculator. See Credits & Sources for full attribution.

Overview & Architecture

The codebase is a strict two-layer split:

  • sailplane_calc/engine/ — pure computation. Every function takes a small @dataclass input and returns a @dataclass result. Nothing in this package imports Qt, touches global state, or does I/O. Every formula here can be called and tested in isolation (see Testing).
  • sailplane_calc/ui/ — PySide6 widgets. One file per tab, plus a handful of shared helpers. UI code never computes anything aerodynamic itself — it only reads input widgets, builds an engine input dataclass, calls an engine function, and writes the result dataclass's fields back into result labels or a hand-painted chart.

The single source of truth: AppState

ui/app_state.py holds every raw input value in the app as plain attributes (floats, strings, small dataclasses) on one AppState object, shared by reference across every tab. There is no per-tab local state and no Redux-style action dispatch — a tab widget just does setattr(self.state, "span1", value) then calls self.state.notify(), which emits a Qt changed signal. Every tab connects state.changed to its own refresh() method in its constructor, so every tab recomputes and repaints on every change anywhere in the app — simple, always-consistent, and fast enough at this problem size that no dependency tracking is needed.

AppState also exposes *_result()/*_input() methods (e.g. wing_result(), cl_distribution_result()) that build the relevant engine input dataclass from its raw attributes and call the matching engine function. These are the seam between the two layers — a tab never calls an engine.* function directly with hand-built inputs; it goes through AppState.

The unit-conversion boundary

Every engine formula works exclusively in fixed canonical units: inches, ounces, mph, degrees. Metric is purely a display-layer concern, handled entirely in ui/units.py: a value is converted to the display system only at the moment it's shown in a widget or read back out of one (UnitSpinBox does this automatically). This means no engine formula ever needs to know or care which unit system the user has selected.

models.py engine/models.py

Every input and result type in the engine is a plain @dataclass defined here, grouped roughly by tab. There's no inheritance-heavy modeling — the one exception is WingPanelInput(PanelInput), which adds dihedral_rise and twist_tip_deg to the generic trapezoidal PanelInput (span, chord_root, chord_tip, sweep_offset) used by every surface (wing, stab, fin, V-tail). Field names and units intentionally mirror the original workbook's cell names so a result can be checked cell-for-cell against SailplaneCalc.xls.

geometry.py engine/geometry.py

The shared trapezoidal-panel math every lifting surface (wing, horizontal stab, vertical fin, V-tail) ultimately reduces to. A "surface" here is a chain of one or more trapezoidal panels; compute_surface(panels, mirrored) walks them root-to-tip, accumulating span and sweep, and produces one aggregate SurfaceResult.

Per-panel trapezoid formulas

For a single panel with root chord cr, tip chord ct, span b, and LE sweep offset Δx (the horizontal distance the tip's leading edge sits aft of the root's):

area = b · (cr + ct) / 2

Mean Aerodynamic Chord (MAC) — the standard trapezoidal-wing formula (e.g. Raymer, Aircraft Design: A Conceptual Approach), rearranged into a form that avoids a division by zero when cr=ct=0:

MAC = (2/3) · (cr + ct − crct/(cr+ct))

which is algebraically identical to the more familiar MAC = (2/3)·cr·(1+λ+λ²)/(1+λ) with taper ratio λ = ct/cr. This is always ≥ the simple area/span "mean chord", since MAC weights the wider (root-ward) part of a tapered panel more heavily — it's the chord of an imaginary untapered wing with the same area, span, and pitching-moment behavior as the real tapered one.

25%-MAC point (panel_25pct_from_own_root), i.e. the panel's own aerodynamic center, measured aft from its own root leading edge:

x25 = Δx · (cr+2ct) / (3·(cr+ct))  +  MAC / 4

The first term is the LE-sweep offset evaluated at the spanwise station where the local chord equals the MAC (the classic ȳ = (b/6)·(cr+2ct)/(cr+ct) formula, with Δx substituted for b since we only need the chordwise, not spanwise, position here); the second term is simply 25% of the MAC length itself. Adding them gives the standard aircraft-design recipe for where a trapezoidal panel's own aerodynamic center sits.

MAC's own spanwise station (panel_mac_span_location) — where along the span the local chord equals the MAC length:

yMAC = b · (cr − MAC) / (cr − ct)   (= b/2 if cr=ct, i.e. untapered)

LE sweep angle is simply atan(Δx / b), purely informational (not used in any downstream aerodynamic formula).

Aggregating panels into a surface

compute_surface area-weights each active panel's own 25%-point, MAC length, and MAC span-location across the whole chain (root to tip), giving the surface as a whole a single effective aerodynamic-center location, MAC, and MAC span station — the same technique used for any multi-panel/cranked wing. mirrored=True (used for every span-defined- as-half-span surface: wing, stab, V-tail) doubles the raw half-surface's span and area to get the full aircraft-wide totals.

mean_chord = total_area / total_span aspect_ratio = total_span / mean_chord   (equivalent to the more familiar b²/S, since S = b·mean_chord) point_0 = (area-weighted x25) − MAC·0.25  (the LE of the surface's own MAC) point_25 = point_0 + MAC·0.25  (the surface's aerodynamic center)

taper_ratio for a multi-panel surface is not simply tip/root — there's no single well-defined value for a cranked planform — so it's backed out from the already-computed mean_chord as an equivalent single-taper value: 2·mean_chord/root_chord − 1 (the inverse of mean_chord = cr·(1+λ)/2 for an untapered-panel equivalent).

safe_div(a, b) is used everywhere a formula divides by a geometry-derived quantity that can legitimately be zero mid-edit (e.g. every panel span cleared) — it returns 0.0 instead of raising, so a transient invalid geometry degrades every tab's display gracefully rather than crashing the whole app on every keystroke.

wing.py engine/wing.py

Dihedral chain

Each WingPanelInput.dihedral_rise is a cumulative measurement — the vertical rise at that panel's tip, measured from the wing-root plane (what you'd read off a ruler held flat against the root). incremental_rise() differences consecutive panels' cumulative rise to get each panel's own rise, then compute_panel_dihedral_deg treats each panel as a rigid rod of length = its span (the slant length) with vertical rise = its own incremental rise, so:

dihedrali = asin(rise_diffi / spani)

(the asin argument is clamped to [−1, 1] before the call — a rise larger in magnitude than its own panel's span is physically extreme but reachable mid-edit, e.g. shrinking a span below an already-entered rise; clamping saturates the angle at ±90° instead of raising a domain error.)

Effective (dihedral-projected) wing

A panel with dihedral is a slant length in 3-D; its aerodynamically-relevant span (what actually contributes to induced drag / lift-curve slope via aspect ratio) is its horizontal projection. Since span is the hypotenuse and rise_diff the vertical leg of a right triangle:

effective_spani = √(spani² − rise_diffi²)

compute_effective_wing rebuilds a whole second EffectiveWingResult (span, area, mean chord, aspect ratio) from these projected per-panel spans — always ≤ the raw "Total Wing Results" for any wing with dihedral. This same projection is reused by cl_distribution.py to build its flat-plane vortex geometry.

Wing loading & Reynolds number estimate

wing_loading [oz/ft²] = weight[oz] / total_area[in²] · 144
Re ≈ 9360 · V[mph] · mean_chord[ft]

The Reynolds number estimate is the standard Re = V·c/ν (velocity times characteristic length over kinematic viscosity), pre-multiplied out for convenient mph/inch inputs. Converting V[mph] to ft/s (×5280/3600 ≈ 1.467) and dividing by air's kinematic viscosity at sea level (ν ≈ 1.57×10⁻⁴ ft²/s) gives a combined constant of 1.467/1.57×10⁻⁴ ≈ 9340 — matching the 9360 constant in the code to within the usual spread of published air-property tables. mean_chord is converted from inches to feet (×1/12 ≈ 0.0833) before multiplying.

flight_performance.py engine/flight_performance.py

A from-scratch re-derivation of the workbook's stall-speed/Cl/G-load calculator, deliberately not transliterating its original tangled unit-conversion chain — independently cross-checked in SI units against the reference workbook's own worked example before being adopted (see the module's own docstring). Everything follows directly from the standard level-flight lift equation:

L = CL · ½ρV²S     (level flight: L = W)

using sea-level standard air density ρ = 0.002378 slug/ft³. The three functions are this equation solved for three different unknowns:

FunctionSolves forFormula
cl_from_stall_speedCL, given V CL = W / (½ρV²S)
stall_speed_from_clV, given CL V = √(W / (½ρCLS))
g_load_at_speedG, given CL and V G = (CL·½ρV²S) / W

g_load_at_speed answers "if the wing is held at this same lift coefficient (angle of attack) but flown at a higher speed, how many G's of lift does it generate relative to level-flight weight?" — used with MAX_SPEED_MULTIPLIER = 4.0 (an assumed dive-speed-to-stall-speed ratio, a common RC sizing rule of thumb) to estimate the structural G-load at that dive speed.

tail_cruciform.py engine/tail_cruciform.py

compute_horizontal_stab is a thin wrapper — the stabilizer is just a single mirrored panel through compute_surface.

The vertical fin is more subtle: its lower and upper panels both root at the same shared center chord but extend in opposite directions from it (down / up), unlike the wing's chained root→tip1→tip2→… panels. compute_vertical_fin re-derives the area-weighted aggregation from geometry.py's per-panel building blocks directly (rather than calling compute_surface, which assumes a chain), assigning the lower panel's MAC-span contribution a negative sign and the upper panel's a positive one — a coherent "below/above the fuselage centerline" sign convention rather than a placeholder.

tail_vtail.py engine/tail_vtail.py

A V-tail panel's own dihedral (half-angle from horizontal) and the included angle between the two V panels. The panel's span is a physical/slant length — a ruler measurement along the panel, the same convention the Wing tab's own panels use — with dihedral_rise the vertical rise over that length, so the half-angle is asin(rise/span), not atan (confirmed against the V-Tail reference workbook's own formula; the two differ substantially at the larger dihedral angles typical of a V-tail, e.g. 46° vs. 33° for a 14.9"-rise/20.65"-span panel):

half_dihedral = asin(dihedral_rise / span) total_angle = 180° − 2 · half_dihedral

compute_vtail's point_0/point_25 are compute_surface([panel], mirrored=True)'s own general area-weighted aggregation, unmodified — an earlier version of this port reproduced a workbook quirk from the original imperial SailplaneCalc.xls where the "25% point" formula divided by the panel's own (single-side) area instead of the mirrored total, but the newer V-Tail reference workbook's own equivalent cells confirm that quirk does not persist there: its formula reduces algebraically to the same general aggregation `compute_surface` already produces, so no override is needed.

Equivalent horizontal/vertical stabilizer areas

The Neutral Point and Tail Sizing Checks formulas (below) are shared with the cruciform tail's separate horizontal stabilizer and vertical fin — for a V-tail, one physical panel must stand in for both. compute_vtail_equivalent_areas splits the V-tail's own total area by its dihedral angle:

horizontal_equivalent_area = total_area · cos²(half_dihedral) vertical_equivalent_area = total_area · sin²(half_dihedral)

confirmed against the V-Tail reference workbook's Balance Point sheet. This is a materially different relationship from vtail_convert.vtail_to_conventional's tangent-based split (a linear 2·v_half_area/(1+tanθ), vs. this quadratic cos²/sin² split of the total area) — the two functions serve genuinely different purposes and are not interchangeable: this one feeds the shared CG/tail-checks formulas from the V-tail's actual geometry, while vtail_to_conventional is a standalone "what-if" conversion tool for the Quick V-Tail Sizing tab only.

neutral_point.py engine/neutral_point.py

Implements a tail-volume-coefficient neutral-point estimate (credited to Martin Simons, Model Aircraft Aerodynamics), with a Helmbold-style aspect-ratio correction to each surface's lift-curve slope and an empirical downwash factor.

Helmbold's equation

A 2-D airfoil's lift-curve slope (thin-airfoil theory: 2π/rad ≈ 0.11/deg) overpredicts a real, finite-span surface's slope — induced downwash from the wingtip vortices reduces the effective angle of attack seen by each section. Helmbold's equation is a well-known empirical correction for this:

a = (AR · a0) / (AR + 18.25 · a0)

where a0 is the uncorrected (2-D, "infinite aspect ratio") per-degree lift-curve slope. The wing uses a0=0.11/deg (close to thin airfoil theory); the tail surfaces use a slightly lower a0=0.095/deg, reflecting a typically thinner/lower-camber tail section.

Tail volume coefficient

VH = (Stail · ltail) / (Swing · c̄wing)

the classic non-dimensional "how big and how far away is the tail" number, where the tail arm ltail is the distance from the wing's own aerodynamic center (its 25%-MAC point) to the tail's aerodynamic center, threading through the wing root chord and the wing-trailing-edge-to-tail-leading-edge gap the user enters. For a V-tail, the dihedral projection already lives entirely in horizontal_equivalent_area (see compute_vtail_equivalent_areas's cos² term) — compute_neutral_point_vtail applies no further dihedral correction to either the tail volume or the stabilizer's own lift-curve slope, matching the reference workbook's Balance Point sheet, which has no separate cosine term in either formula.

Neutral point & static margin

downwash_factor (dε/dα) ≈ 35 · awing / ARwing NP [% MAC] = (0.25 + η · VH · (atail/awing) · (1 − dε/dα)) · 100

This is the standard stick-fixed static-longitudinal-stability neutral-point formula: the wing's own aerodynamic center (25% MAC) plus a stabilizing contribution from the tail, proportional to how big/far the tail is (VH), how effective it is relative to the wing (atail/awing), how much of the tail's own angle of attack survives the wing's downwash (1−dε/dα), and an overall efficiency factor η (the user-entered Stabilizer Efficiency, ~0.6 for a cruciform tail sitting in the wing's wake, ~0.9 for a T-tail clear of it). static_margin = NP[%MAC] − CG[%MAC] follows directly, and compute_balance_point is pure algebra converting between the three equivalent ways of specifying a CG location (static margin %, %MAC, or an absolute distance from the root leading edge) so that switching which one you're typing into never silently reinterprets a stale number under a new meaning — a trap the original spreadsheet falls into whenever a formula cell gets overwritten with a plain number.

tail_checks.py engine/tail_checks.py

Mark Drela's non-dimensional tail-sizing design-check parameters (Radio Controlled Soaring Digest, Aug 2004) — a second, independent set of tail-sizing numbers alongside the neutral-point calculation, aimed specifically at RC sailplane handling qualities (spiral stability, thermalling behavior) rather than generic longitudinal stability.

Equivalent Dihedral Angle (EDA)

A single spanwise-weighted dihedral number standing in for a wing whose dihedral angle varies from panel to panel (polyhedral). Each panel is weighted by how much its outboard edge's position on an elliptical-lift-like falloff curve f(η) = (1−η²)1.5 (where η is spanwise fraction, 0 at root, 1 at tip) differs from its inboard edge's:

EDA = Σi (f(ηi) − f(ηi+1)) · dihedrali

— effectively integrating dihedral against a weighting curve that concentrates more importance on inboard panels (where most of an elliptically-loaded wing's lift, and hence its contribution to roll/yaw coupling, is concentrated).

Tail volumes & spiral stability

VH = (Sh/Sw) · (gap + x25,h + 0.75·(c̄w+x0,w)) / c̄w Vv = (Sv/Sw) · (gap + x25,v + 0.75·(c̄w+x0,w)) / bw b (spiral stability) = EDA · (vertical arm term) / CL,therm

This reproduces Drela's own published recipe exactly (the horizontal volume normalizes the tail-arm term by wing mean chord, the vertical volume by wing span — the standard convention for horizontal vs. vertical tail volume coefficients). b combines the equivalent dihedral with the vertical tail's effectiveness, divided by the assumed lift coefficient during slow thermalling flight (a user-entered setting on the Tail Sizing Checks tab) — Drela's suggested interpretation bands (b>5 stable, b=5 neutral, b<5 unstable) are reproduced verbatim in that tab's on-screen help text.

vtail_convert.py engine/vtail_convert.py

Bidirectional conversion between a conventional (horizontal + vertical) tail and a V-tail of equivalent total area, for the Quick V-Tail Sizing tab. Treating the horizontal and vertical areas as the legs of a right triangle and the V-tail's half-area as the hypotenuse-equivalent:

v_half_area = (horizontal_area + vertical_area) / 2 half_dihedral = atan2(vertical_area, horizontal_area)

atan2 (rather than atan(vertical/horizontal)) is used specifically so a zero horizontal area — reachable just by clearing that input field — gives a well-defined 90° instead of a division-by-zero crash. The inverse direction solves the same relationship for the two areas given a V-half-area and a dihedral angle:

horizontal_area = 2·v_half_area / (1 + tan(θ)) vertical_area = horizontal_area · tan(θ)

guarded against the denominator approaching zero near −45° dihedral (reachable from an extreme negative dihedral rise), which would otherwise blow up to an astronomical, meaningless area instead of cleanly returning zero.

planform.py engine/planform.py

Pure 2-D outline geometry for drawing, not analysis — walks panels the same way geometry.compute_surface does (cumulative span/sweep) but keeps every breakpoint as a polygon vertex instead of reducing to aggregate scalars. compute_planform_outline traces one closed root-to-tip-and-back polygon (used by the vertical-tail side view and single-surface previews); compute_planform_panels instead returns one quad per panel, each tagged with its panel index so the widget can color panels distinctly, mirrored to both sides for a symmetric surface. Mirroring negates the span coordinate and reverses point order so a full-span point list still reads root→tip consistently across the whole wing — the same left/right convention cl_distribution.py reuses for its own vortex geometry.

cl_distribution.py engine/cl_distribution.py

The most numerically involved module in the engine: a horseshoe-vortex Vortex Lattice Method (VLM) — the same family of method as LIFTROLL.xlsx (John Hazel's Lift and Cl calculator), reimplemented from the standard aerodynamic theory rather than transcribed cell-by-cell, and wired directly into the app's existing 4-panel wing geometry (no new inputs beyond twist). It answers a question none of the other engine modules do: how is lift distributed along the span, not just how much lift the wing makes in total.

Why a lattice of horseshoe vortices?

Classical thin-airfoil theory gives a 2-D section's lift, but a real finite wing's local lift coefficient at any span station depends on the whole wing's planform — its taper, sweep, and twist all redistribute lift along the span, and induced downwash from the trailing vortex sheet reduces the effective angle of attack seen at each station. The Vortex Lattice Method (see e.g. Katz & Plotkin, Low-Speed Aerodynamics, or Bertin & Cummings, Aerodynamics for Engineers) models this by replacing the wing's bound circulation with a row of horseshoe vortices — one per spanwise strip — each a closed loop of a finite bound segment (at the strip's quarter-chord) plus two trailing legs running downstream to (effectively) infinity, and solves for every vortex's circulation strength simultaneously so that the flow is tangent to the wing surface at every strip's control point (its three-quarter-chord point). This app uses one lifting line per panel-strip in a single flat (chordwise, spanwise) plane — the same simplification LIFTROLL.xlsx's own 2-D vortex-corner storage makes — using each panel's dihedral-projected span (see wing.py's incremental_rise) rather than modeling dihedral's out-of-plane geometry directly.

1. Geometry: from 4 panels to up to 40 vortices

_build_span_stations walks the wing's (up to) 4 active panels — the same root/sweep/twist chaining geometry.py and planform.py use — and subdivides each into N_STATIONS_PER_PANEL = 5 equal-width spanwise strips, linearly interpolating chord, LE offset, and twist at each strip's edges and midpoint. 4 panels × 5 strips × 2 (mirrored) sides = up to 40 vortices, matching LIFTROLL.xlsx's own fixed 40-vortex grid. Each strip becomes one horseshoe vortex:

  • a bound segment at 25% of the local chord, spanning the strip's left and right edges;
  • a control point at 75% of the local chord, at the strip's spanwise midpoint — where the flow-tangency boundary condition is enforced;
  • two trailing legs, extending downstream from the bound segment's endpoints to TRAILING_LEG_LENGTH_FACTOR = 100 span-lengths away — a standard, well-known long-but-finite stand-in for a true semi-infinite vortex filament (the residual induced velocity beyond that distance is negligible), which lets one finite-segment formula serve both the bound and trailing legs.

The classic quarter-chord/three-quarter-chord placement (rather than, say, both at the same chordwise station) is what makes a single chordwise lifting line correctly reproduce a thin airfoil's 2-D lift-curve slope in the limit of an isolated, high-aspect-ratio strip — a well-established result from thin-airfoil/lifting-line theory.

2. Biot-Savart induced velocity

Every vortex point and every control point lies in the same flat plane (dihedral is projected away, see above), which has a useful consequence: for a filament and field point both confined to a plane, the 3-D Biot-Savart cross product dℓ × r always points purely normal to that plane. So the only induced-velocity component that ever matters here is the scalar downwash w, computed by the standard closed-form finite-vortex-segment Biot-Savart formula for a unit-circulation filament from point A to point B, evaluated at point P:

r1 = P−A, r2 = P−B, r0 = B−A w = (1/4π) · [(r0·r1)/|r1| − (r0·r2)/|r2|] / (r1×r2)z

(_segment_induced_w in the code, guarded against the near-singular case where the field point sits essentially on the filament itself). A full horseshoe's induced velocity at any point is the sum of this formula applied to its three segments — far-left-to-left trailing leg, left-to-right bound segment, right-to-far-right trailing leg — traversed as one continuous circulation loop (_horseshoe_induced_w). Stacking every vortex's induced velocity at every control point builds the Aerodynamic Influence Coefficient (AIC) matrix: a square matrix where AIC[i][k] is the downwash induced at control point i by a unit circulation on horseshoe k.

3. Boundary condition & the linear solve

Flow tangency (no flow through the lifting surface) requires the total induced downwash at each control point to exactly cancel the local geometric angle of attack (freestream normalized to unit magnitude, so the solved circulation is really Γ/V∞ throughout — the freestream speed cancels out of every quantity this module needs):

Σk AIC[i][k] · γk = −αlocal(i)

Rather than solving this once per flight condition, the module exploits that this system is linear in angle of attack: it's solved once, with two independent right-hand sides — one for the wing's own built-in twist alone (RHStwist[i] = −radians(twisti)), and one for a uniform 1-radian addition to every station's angle of attack (RHSunit[i] = −1) — via linalg.solve_linear_system's multi-column solve (one matrix decomposition, two right-hand-side columns). The resulting two circulation solutions, γtwist and γunit, are then combined by superposition for any root angle of attack αroot:

γ = γtwist + αroot · γunit

4. Matching a target lift coefficient — no goal-seek needed

The overall wing lift coefficient is itself a linear functional of γ (a weighted sum, see below), so αroot that makes the wing's overall CL exactly equal a target value can be solved in one division rather than an iterative goal-seek (the way LIFTROLL.xlsx's own Excel Solver finds its trim conditions):

CL(γ) = Σi (2·γi·widthi) / Stotal αroot = (target_CL − CL(γtwist)) / CL(γunit)

The target_CL is the aircraft's overall CL at stall speed (AppState.speed_performance()'s cl, already computed on the Wing tab from weight/area/stall-speed — see flight_performance.py) — matching the module's purpose, per LIFTROLL.xlsx's own description: "the Local Cl graph can help find where the wing will stall first." Stotal is deliberately the same raw (non-dihedral-projected) wing_result().surface.total_area that target_CL was itself computed against, so the two stay on a consistent basis even though the vortex geometry itself uses the dihedral-projected span.

5. Local Cl, local lift, and the elliptical reference

From Kutta-Joukowski, local lift per unit span is l' = ρVΓ; combined with the definition of a local lift coefficient l' = Cl·q·c (with q=½ρV²), and using the same V∞=1 normalization as above:

local_lifti = Cl,i·ci = 2·γi Cl,i = local_lifti / ci

The ideal elliptical reference curve — Prandtl's classic result that an elliptical spanwise lift (not chord) distribution minimizes induced drag for a given span and total lift, the textbook benchmark every real planform is compared against — is built directly from the solved distribution's own total lift, not a second VLM solve. Since ∫−b/2b/2 √(1−(y/(b/2))²) dy = (b/2)·π/2:

L0 = 2 · total_lift / (π · half_span) ellipse_lift(y) = L0 · √(max(0, 1 − (y/half_span)²))

guaranteeing the ellipse curve carries exactly the same total lift as the actual solved distribution, so the two curves are directly comparable by eye on the Cl Calcs tab's "Lift Distribution vs Ideal Ellipse" chart.

Deliberately out of scope: LIFTROLL.xlsx also models aileron deflection and roll rate, using Excel Solver to goal-seek a steady-rolling trim condition. This port omits that entirely — the app has no aileron/roll-rate inputs anywhere else, and the same closed-form superposition trick used above for angle of attack extends cleanly to a roll trim (two more RHS columns, then one more division instead of a goal-seek) if that's ever wanted; see the "Proposed future extension" section of the implementation plan this module was built from.

linalg.py engine/linalg.py

A small, deliberately VLM-agnostic dense linear-system solver — solve_linear_system(a, b) solves A·x = B for an N×N matrix A and an N×M right-hand side B (M independent right-hand-side columns solved together off one decomposition, which is exactly how cl_distribution.py uses it). Implemented as textbook Gauss-Jordan elimination with partial pivoting: for each column, the row with the largest-magnitude entry in that column (among remaining rows) is swapped into the pivot position before eliminating, which avoids the numerical instability of dividing by a small or zero pivot that naive top-to-bottom elimination is prone to. A still-near-zero pivot after searching (a genuinely degenerate column, e.g. from a zero-span panel mid-edit) is left as a decoupled identity row rather than raising — the same crash-avoidance convention as geometry.safe_div, extended to linear algebra. No external numeric library (e.g. NumPy) is used anywhere in this app; for the matrix sizes involved here (≤40×40), a hand-rolled solver is simple, dependency-free, and plenty fast for a live-refreshing UI.

app_state.py ui/app_state.py

Already introduced in Overview & Architecture. Concretely: every raw input is a plain attribute (e.g. self.span1, self.chord_root, self.twist1_deg), and each tab's data need is exposed as a small accessor method, for example:

def wing_panels(self) -> list[WingPanelInput]:
    return [
        WingPanelInput(span=self.span1, chord_root=self.chord_root, chord_tip=self.chord1_tip,
                       sweep_offset=self.sweep1, dihedral_rise=self.rise1, twist_tip_deg=self.twist1_deg),
        ...
    ]

def cl_distribution_result(self):
    cl, *_ = self.speed_performance()
    return compute_cl_distribution(ClDistributionInput(panels=self.wing_panels(), target_cl=cl))

Notice how cl_distribution_result() calls speed_performance() (the Wing tab's stall-speed/Cl calculator) to get its target CL — this is the concrete mechanism behind the cross-tab wiring described in cl_distribution.py above; nothing about it is special-cased, it's the same "build an input dataclass from current state, call the engine, return the result" pattern every other *_result() method follows.

One piece of actual (non-pass-through) logic lives here: switch_balance_mode recomputes the stored balance-point value when the user switches which of static margin/%MAC/distance they're specifying, so the physical CG location is preserved across the switch rather than reinterpreting a stale number under the new mode's units (see neutral_point.py).

config_io.py ui/config_io.py

Save/load the entire AppState to/from a JSON file, standing in for Excel's implicit cross-sheet cell references. _SCALAR_FIELDS is an explicit allow-list of every plain-attribute input (adding a new input, like the Wing tab's twist fields, means adding its name to this list); _PANEL_FIELDS lists the small dataclass-valued attributes (stab_panel, fin_lower, fin_upper, vtail_panel), serialized via dataclasses.asdict. apply_dict_to_state is deliberately tolerant of missing keys, so a config file saved by an older version of the app (before a new field existed) still loads cleanly — only the fields actually present in the file are applied.

widgets.py ui/widgets.py

Small shared helpers that keep every tab's construction code declarative:

  • make_spin(value, on_change, ...) — a plain QDoubleSpinBox for unit-agnostic fields (angles, ratios, efficiencies, Cl values) that never go through the imperial/metric conversion.
  • UnitSpinBox — a QDoubleSpinBox subclass that stores/emits a canonical engine-unit value but displays it converted to the app's current unit system, with the matching suffix. Its sync() method is called from every tab's refresh() (itself triggered by state.changed, including a unit toggle) to re-pull the canonical value and re-render it in whichever unit system is now active.
  • add_result_row(layout, caption) — a bold, non-editable QLabel for a computed (read-only) result, added as a QFormLayout row.

Every spin box in the app — both helpers here, and the two places that still construct a raw QDoubleSpinBox directly (the Wing tab's stall-speed/Cl value spinner, and BalancePointBox's value spinner) — is capped at SPIN_BOX_MAX_WIDTH pixels. Left uncapped, Qt's default QFormLayout field-growth behavior stretches every input box to fill its whole column, pushing the increment/decrement arrows far to the right of the actual value; a fixed max width keeps the arrows snug against the value across every tab in the app.

Tabs ui/*_tab.py

One file per tab, each following the same shape: a QWidget subclass whose constructor builds QGroupBox/QFormLayout sections of input widgets (via widgets.py helpers) and result labels, connects state.changed to self.refresh, then calls self.refresh() once immediately. refresh() re-syncs every spin box, pulls a fresh result from the matching AppState accessor, and re-renders every label/chart from it.

Custom-Painted Widgets ui/*_widget.py

The app has no charting or diagramming library dependency — every diagram is drawn directly with QPainter in a small QWidget subclass. All three follow the same shape: a set_data(...) method stores plain model-space data (inches, degrees — never display units) and calls self.update() to schedule a repaint; paintEvent() computes a plot_rect inset from the widget's own bounds, builds a small to_widget(x, y) -> QPointF closure mapping model-space coordinates into that rect, and draws with it — only the corner/axis text labels ever call into units.py for display-unit conversion.

  • PlanformWidget — a wing/tail/fin outline: filled, one color per panel (from planform.compute_planform_panels), with a dashed MAC line and a triangle marking the 25%-MAC aerodynamic-center point. Uses a single uniform scale for both axes (_make_transform picks min(width/span_range, height/chord_range)) so the drawn shape is true to the real planform's proportions, not stretched to fill the widget.
  • BalanceDiagramWidget — a single reference bar spanning the root chord, with the MAC segment highlighted, the Neutral Point marked with a dashed line + triangle, and the CG marked with a diamond; tints the whole background red as a visible warning whenever the NP is forward of the CG (a statically unstable balance point).
  • XYChartWidget (Cl Calcs tab only) — a generic line chart taking a list of ChartSeries (label, color, points, optional dashed style). Unlike PlanformWidget, its x and y axes scale independently, since a span-in-inches axis and a dimensionless-Cl axis have unrelated magnitudes; draws light gridlines with numeric labels, an explicit zero-line when the data straddles zero, and a small legend when more than one series is plotted.

main_window.py ui/main_window.py

Builds the single QTabWidget and registers every tab, each wrapped in a scrollable container (_scrollable()) so a narrow window never clips content. Cruciform-tail and V-tail tabs are registered like any other, but their addTab() return value (the tab's index) is captured, so _update_tab_visibility() — connected to state.changed — can show only the matching set based on state.tail_type. Tabs with no such dependency (Setup, Wing, Cl Calcs, Quick V-Tail Sizing, Tail Sizing Checks) are always visible and need no index bookkeeping at all.

Testing

tests/ mirrors engine/ file-for-file (tests/test_<module>.py); there are no UI tests, matching the codebase's strict computation/presentation split — every formula worth testing lives in a pure function the test suite can call directly. Two distinct testing styles show up, depending on whether a spreadsheet-derived ground truth exists:

  • Regression against a worked example (most modules, e.g. test_wing.py, test_metric_reference.py) — the same input geometry as SailplaneCalc.xls's own documented worked example, asserting the computed results match its published numbers to a tight tolerance. This is what "port, don't reinvent" verification looks like: if a formula changes and these tests still pass, the port is still faithful to the reference tool.
  • Structural/invariant tests (test_cl_distribution.py, test_linalg.py) — for the VLM, which is a fresh implementation of a standard method rather than a transcription of any spreadsheet's cells, there's no golden-value ground truth to regress against. Instead these tests check the invariants the method must satisfy regardless of the exact numbers: left/right symmetry for an untwisted wing, total-lift conservation (the integrated CL matches the requested target), exact linearity when scaling the target CL, and an isolated closed-form check of the Biot-Savart segment helper against the textbook infinite-straight-vortex result.

tests/test_config_io.py's round-trip test is fully generic — it iterates _SCALAR_FIELDS/_PANEL_FIELDS directly, so a newly added input field (like the Wing tab's twist fields) is automatically covered the moment it's added to config_io.py's field list, with no test file changes needed.
